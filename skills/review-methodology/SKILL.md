# 评审方法论（Review Methodology）

面向变更、配置、安全与爆炸半径的专业评审标准。本舰队里，评审是 **`draft` 起草之后、人工应用之前**的那道自审——把"起草"和"批准执行"之间的白区补齐。

## 自主性对齐

评审运行在 `recommend` 层：产出"通过 / 阻断 + 证据 + 严重度"，**不应用任何变更**。

| 动作 | 层级 | 说明 |
|------|------|------|
| 读变更工件与其证据基线 | observe | MR diff、overlay、Impact/Baseline 证据 |
| 出评审结论与阻断判断 | recommend | 通过/阻断、发现项、严重度、下一步 |
| 应用变更 | act | **无人**——评审通过也仅解除自审阻断，仍需人工闸门批准执行 |

评审"通过"≠ 变更被应用。它只是允许这份草稿进入人工闸门，人仍是最终执行者。

## 评审类型

| 类型 | 何时用 | 重点维度 |
|------|--------|----------|
| **变更评审** | gitops-agent 起草了 MR/overlay/配置 diff | 意图对齐、正确性、可回滚性、灰度/爆炸半径 |
| **配置/GitOps 评审** | Kustomize overlay、Helm values、ArgoCD Application 变更 | 环境隔离、密钥不入库、副本/资源/探针、sync 策略 |
| **安全评审** | 变更触及 RAM/密钥/网络策略/镜像 | 最小权限、密钥泄露、暴露面、供应链 |
| **爆炸半径评估** | 任何触及线上的变更进人工闸门前 | 影响范围、容量余量、并发/依赖冲击、回滚代价 |

## 评审心法（所有类型同一条弧线）

1. **理解意图** —— 这个变更想达成什么？先读 MR 描述、关联事件/工单、诊断根因。脱离意图的评审毫无意义。
2. **评估正确性** —— 它真能达成既定目标吗？先于风格与优雅。配置改对了字段吗？选对了目标环境吗？
3. **评估质量** —— 对其目的而言构造是否得当？可维护性、幂等性、是否夹带无关改动、是否可回滚。
4. **评估风险** —— 会出什么问题？边界条件、密钥/权限、回归、容量与并发冲击、灰度是否覆盖。
5. **清晰沟通** —— 发现项按严重度组织，给可执行的下一步。对事不对人。

**绝不在理解意图与正确性之前跳到质量或风格。** 一个风格优美却解决错问题的变更，仍然是错的。

## DevOps 专用检查清单

**变更/配置：**
- [ ] 变更目标环境正确（没把 prod 当 test）、命名空间/集群无误
- [ ] 可回滚：有明确回滚路径（revert MR / 上一个 image tag / 上一个 overlay）
- [ ] 幂等：重复 apply 结果一致，不依赖手工前置步骤
- [ ] 无关改动已剔除，diff 只包含本次根因对应的修复
- [ ] 副本数、resource requests/limits、探针（liveness/readiness）合理

**安全：**
- [ ] 无明文密钥/AccessKey/token 入库（用 Secret/外部密钥管理）
- [ ] RAM/RBAC 遵循最小权限，没有顺手放大 scope
- [ ] 网络策略/暴露面没有意外放开（SLB、SecurityGroup、Ingress）
- [ ] 镜像来源可信、tag 固定（非 latest 漂移）

**爆炸半径（进人工闸门前必答）：**
- [ ] 影响哪些服务/租户/区域？范围是否已在证据里量化
- [ ] 当前容量余量能否吸收本次变更（对照 observability 基线）
- [ ] 有没有并发/依赖冲击（连接池、限流、上下游雪崩）
- [ ] 是否已捕获"变更前"基线，供应用后验证对照

## 评审结论模板

```
裁决：通过 / 阻断
意图：<这个变更想解决的根因/目标>
正确性：<是否达成目标；证据>
发现项（按严重度）：
  - [阻断] <必须先解决才能进人工闸门的问题>
  - [重要] <应解决>
  - [提示] <可选优化>
爆炸半径：<范围 / 容量余量 / 回滚代价>
下一步：<给人工闸门的明确动作，或退回 gitops-agent 重新起草>
```

## 反模式

- **未观测就评审。** 没有 Impact/Baseline 证据的草稿，评审无从判断爆炸半径——退回，先取证。
- **评审通过 = 已上线。** 通过只解除自审阻断，执行仍是人工闸门的人。别在结论里暗示"已应用"。
- **只审风格不审正确性。** 字段拼写整齐但改错了环境/目标，照样阻断。
