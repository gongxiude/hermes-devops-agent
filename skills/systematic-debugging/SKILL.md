# 系统性调试（Systematic Debugging）

## 概述

盲目试修浪费时间、还会制造新故障；打补丁只会掩盖底层问题。

**核心原则：任何修复动作之前，必须先拿到根因。** 只针对症状的修复等于失败。

## 铁律

```
未完成根因调查，不得起草任何变更
```

在本舰队里这条铁律和路由铁律重合：**先取证据，再谈变更。** 没有走完 Phase 1，就不能把任务路由给 `gitops-agent` 起草修复。

## 自主性对齐

诊断全程运行在 `observe` / `recommend` 层，不越界：

| 动作 | 层级 | 谁 |
|------|------|-----|
| 采集指标/日志/资源状态证据 | observe | observability, infra-agent |
| 形成根因假设与风险判断 | recommend | orchestrator 合成 |
| 把根因表达为一个变更工件（MR/overlay） | draft | 仅 gitops-agent，起草后**人工闸门** |
| 应用变更（scale/rollback/restart/patch…） | act | **无人**——输出为 `next human action` |

诊断产出的是"根因 + 建议动作"，不是线上执行。

## 何时使用

任何运行时问题：服务劣化/宕机、告警风暴、指标或日志异常、发布后回归、容量/延迟问题、组件间集成故障。

**尤其在：** 故障压力大（越急越想猜）、"就改一个参数试试"看似显然、已经试过多次修复、上一次修复没生效、你其实没完全搞懂问题时。

**不要因为下列理由跳过：** "问题很简单"（简单故障也有根因）、"在赶时间"（乱试保证返工）、"有人要求立刻恢复"（系统性诊断比反复试错更快）。

## Phase 1：根因调查

**在尝试任何修复之前：**

### 1. 认真读错误与告警
- 不要略过错误、告警、异常事件——它们常常直接指向答案。
- 完整读告警标签、日志堆栈、事件时间戳。记录服务名、命名空间、错误码。
- **动作：** 用 observability 拉取相关时间窗的日志/指标；用 infra-agent 查对应资源状态。

### 2. 可靠复现 / 稳定观测
- 现象能稳定复现或持续观测到吗？触发条件是什么？
- 若无法稳定观测 → 继续采数据，不要猜。
- **动作：** 圈定时间窗、服务标签、受影响副本集，让"什么时候坏、坏在哪"可量化。

### 3. 检查近期变更
- 什么变了可能导致它？最近的发布、配置/overlay 变更、依赖升级、扩缩容、AccessKey/scope 调整。
- **动作：** 路由 `gitops-agent` 列出时间窗内的 Jenkins 构建、ArgoCD sync、Codeup MR。**先观测，再看变更**，把现象和变更对齐到一条时间线。

### 4. 多组件系统按边界取证
当链路跨多个组件（入口 → 服务 → 中间件 → DB；CI → 构建 → 部署）时，**逐个边界**取证：
- 每个组件边界，观测进入的流量/数据与流出的结果。
- 校验环境/配置是否正确透传（限流、超时、连接池、探针）。
- 看每一层的状态，定位"在哪一跳断的"，再分析是哪个组件。

### 5. 检查环境/基线分歧
现象只在生产出现、测试环境没有时：
- 对比两环境的资源规格、副本数、限流阈值、连接数、探针配置。
- 检查数据源可达性差异（如测试环境没有 Loki）。**被阻塞的数据源返回 `unknown` 证据，不是"跳过"**，留审计记录。
- 校验容量余量：CPU/内存/连接/磁盘是否已触顶。

### 6. 追踪数据流
错误在调用栈深处时：坏值从哪产生 → 谁用坏值调用了它 → 一路向上游追到源头。**在源头修，不在症状处修。**

### 7. 穷尽本地证据仍不懂时，先研究再猜
用精确错误串 + 平台/版本上下文检索已知问题与确认过的 workaround，读全线程再下结论。不要跳到"大概是 X"就动手。

### Phase 1 完成清单
- [ ] 错误/告警已完整读懂
- [ ] 现象已稳定观测（时间窗、标签、范围明确）
- [ ] 近期变更已列出并与时间线对齐
- [ ] 跨边界证据已采集（日志、指标、资源状态、数据流）
- [ ] 问题已收敛到具体组件/配置
- [ ] 已形成根因假设

**STOP：** 在你能说清"为什么会这样"之前，不要进入 Phase 2，更不要路由起草。

---

## Phase 2：模式分析

- **找可用的对照。** 同集群/同类服务里正常运行的是什么样？正常与异常的差异逐条列出，别假设"这点不可能有影响"。
- **对照参考实现。** 若在实施某种模式（HPA、探针、限流、灰度），完整读参考配置，别只扫一眼。
- **理解依赖。** 这条链路还依赖什么（配置、密钥、上游服务、容量假设）？

---

## Phase 3：假设与验证

- **单一假设。** 明确写下："我认为根因是 X，因为证据 Y。" 具体，不含糊。
- **最小验证。** 一次只动一个变量去验证假设，不要同时改多处。
- **验证再继续。** 成立 → Phase 4；不成立 → 形成新假设，不要在旧修复上层层加码。
- **不懂就说不懂。** "我不理解 X"好过假装懂——继续取证或交人工。

---

## Phase 4：修复（起草，非执行）

**修根因，不修症状。** 本舰队在此止步于 `draft`：

1. **可验证的复现/基线。** 修复前先由 observability 捕获"变更前"基线，否则事后无从验证。
2. **单一修复。** 只针对已确认的根因起草一个变更（gitops-agent 产出 MR/overlay）。不夹带"顺手优化"、不捆绑重构。
3. **人工闸门。** 流水线在起草后暂停，由人审批并应用。舰队不越过这条线。
4. **应用后验证。** 人工应用后，observability 对照 Phase 4.1 的基线验证恢复，闭合 OODA 环。若唯一修复只能是线上 `act`，就停下，输出为一条 `next human action`。

### 三次法则
若起草的修复方向反复被证据推翻：数到第 3 次就 **STOP**，不要试第 4 次方向——转而质疑架构（是不是模式本身有问题、每次修复都牵出新的耦合/新的症状）。这不是"假设失败"，是"方向错了"，交人工讨论。

---

## 危险信号——立刻停下回到 Phase 1

- "先临时修一下，回头再查"
- "改改 X 看看灵不灵"
- "一次多改几处，跑一下看结果"
- "大概是 X，先修 X"
- 在追踪数据流之前就抛出一堆"修复清单"
- 已经试了 2+ 次方向还要"再试一个"
- 每次修复都在另一个地方牵出新问题

**以上任何一条都意味着：停。回到 Phase 1。** 3+ 次失败：质疑架构。

## 常见借口对照

| 借口 | 现实 |
|------|------|
| "问题简单，不用走流程" | 简单故障也有根因，流程对简单故障也很快 |
| "在救火，没时间走流程" | 系统性诊断比反复试错更快 |
| "先试这个，回头再查" | 第一次修复定调，一开始就做对 |
| "先确认能修再补验证" | 没基线的修复无从验证，也站不住 |
| "一次多改几处省时间" | 分不清哪个起效，还会造新故障 |
| "我看到问题了，直接修" | 看到症状 ≠ 理解根因 |

## 快速参考

| 阶段 | 关键动作 | 完成标准 |
|------|----------|----------|
| **1. 根因** | 读告警、稳定观测、查近期变更、跨边界取证、追数据流 | 说清 WHAT 与 WHY |
| **2. 模式** | 找对照、比参考、逐条列差异 | 知道差在哪 |
| **3. 假设** | 单一假设、最小验证、一次一变量 | 假设被证实或换新假设 |
| **4. 修复** | 捕基线、起草单一变更、人工闸门、应用后验证 | 根因消除、恢复被验证 |
